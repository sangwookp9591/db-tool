# L2 — PG true streaming · MCP 결과 상한

PG true streaming과 desktop MCP의 결과 상한·핸들을 구현했다. ADR-0004·0003, ARCHITECTURE, README, L1 인계와 memory-perf Top 10의 5·6을 기준으로 했다. 시작은 main `90b06e0`의 clean 상태였고 commit/push, 사용자 앱·GUI·사용자 DB·SSH 접근은 없다. 빌드·추출은 `CARGO_TARGET_DIR=target-l2`, `CARGO_BUILD_JOBS=6`과 테스트 임시 경로만 사용했으며 dist/·target/·target-rel은 수정하지 않았다.

PG는 protocol 1 안에서 `Capabilities.execute_stream`을 handshake로 확인한 뒤 선택 `execute_stream`을 호출한다. `stream_start`는 컬럼과 미정 행 수를, `stream_end`는 실제 반환 행 수·elapsed·truncated를 전달한다. 기존 세션 mutex, read_only, 취소·타임아웃·ROLLBACK 경로를 공유하며 텍스트 변환을 재사용해 int8/numeric/JSON 문자열을 보존한다. `simple_query_raw`와 커서 FETCH 200/2,000행, 약 256KiB 배치, SDK 8프레임 async 채널을 연결했다. DML RETURNING/SHOW/EXPLAIN은 raw stream을 drain한다. 기존 execute와 행 상한은 유지하며 선택 실행 시작 뒤 legacy 재실행은 없다. row_limit≤2,000 요청은 기존 경로이고, 큰 행 예산의 PG 요청은 실제 결과가 작아도 즉시 채널을 사용한다.

동일 debug 드라이버의 legacy/streaming을 교차 3쌍 비교했다. 10만 행의 RSS 중앙값은 234.70→44.61MiB, physical footprint는 222.38→18.98MiB, 첫 rows 청크는 865.75→16.74ms, 전체는 2,052.29→1,203.79ms였다. 총 100만 행은 RSS 2,196.06→46.62MiB, footprint 2,184.71→26.83MiB, 첫 청크 8,632.78→18.85ms, 전체 20,459.96→12,886.29ms였다. 기존 결과당 10만 행 상한을 지켜 100만 행은 10개 결과 집합이며 단일 100만 행·호스트 256MiB 상한 초과 전송 근거가 아니다. 느린 소비자 100만 총행의 RSS는 50.97MiB였다. 약 2ms proc_pid_rusage 샘플 최대값이며 빌드 병행·load gate 미적용, driver stdio 경계다. 앱/WebKit footprint, 릴리스 성능이나 L1 +50MiB 목표 달성으로 일반화하지 않는다. [원자료](../bench/results-l2-streaming.json), [요약](../bench/results-l2-streaming-summary.json), [RESOURCE_OPT](RESOURCE_OPT.md)에 근거를 남겼다.

Desktop MCP의 structured 도구 값은 기본 200 items/256KiB이며 클라이언트별 `max_result_rows`(1–1000), `max_result_bytes`(8–1024KiB)를 설정한다. UI forward와 JSON 응답 전 상한을 적용하고 count writer로 큰 값을 별도 문자열화하지 않는다. 기존 MCP text와 structuredContent 표현을 유지하므로 전체 wire envelope는 이 값 예산보다 클 수 있으나 상한의 상수 배수로 제한된다. 초과 원본은 최대 32개·보수적 heap 추정과 JSON 인코딩 예약을 합해 32MiB인 메모리 LRU에 둔다(allocator overhead 별도). 원본이 캐시 한도를 넘으면 `result_handle_unavailable: cache_size_limit`을 명시한다. `get_result_page`는 같은 클라이언트·토큰 해시·연결·살아 있는 세션과 현재 권한으로만 읽고 SQL을 재실행하지 않는다. 큰 셀은 통째로 생략하고 byte_offset/next_byte_offset UTF-8 JSON 조각으로 복원한다. 세션 종료, 설정·권한 변경, 회전·폐기, 브리지 종료와 앱 teardown에서 정리하고 10분 유휴 시 만료한다. 로그에는 행·핸들 대신 잘림 여부만 추가했다. 기존 저장 클라이언트의 allowlist는 보존하므로 페이지 도구를 따로 허용해야 할 수 있다. [AGENT](AGENT.md)에 사용 계약을 적었다.

최종 검증은 workspace bins 빌드, 대상 PG/MySQL·SDK·protocol·dbcore cargo test 52개, MCP/캐시 10개, LiveResults 3개, 호환 8개, 구 설정 기본값·페이지 입력 각 1개, workspace all-targets clippy -D warnings, tsc와 UI 144 passed/1 skipped 통과다. PG와 MySQL/MariaDB는 허용된 로컬 실DB를 사용했고 MySQL require TLS도 실제 cipher를 확인했다. PG TLS 및 MySQL CA verify-full처럼 환경이 없는 early-return은 실서버 검증으로 세지 않는다. 0.2.0 host codec fixture는 d07c12f 원문과 SHA-256이 같고, 실제 0.2.0 PG 패키지에서 manifest SHA-256을 확인한 바이너리로 new-host/old-driver도 검사했다. 새 호스트/새 드라이버의 pending→final도 통과했다. [검증 명세](../bench/results-l2-verification.json), [정리한 로그](../bench/results-l2-validation.txt)에 명령과 범위를 남겼다.

전체 workspace는 green이 아니다. 첫 실행의 Mongo URI fixture 불일치를 수정한 뒤 기본 병렬 검사가 plugin Mongo schema의 전후 카탈로그 동일성 assertion에서 39 passed/1 failed로 중단됐다. 그 사이 같은 테스트 바이너리의 다른 contract가 만든 m1 컬렉션이 추가된 것이 양쪽 차이였다. 실패한 schema fixture의 view·큰 sampled 컬렉션이 다음 별도 실행의 Mongo management/context도 실패시켰다. 이 실행의 정확한 prefix 5개 namespace만 제거했고 schema 단독 진단은 통과했지만, 이를 전체 green으로 바꾸거나 Mongo 코드·테스트를 범위 밖에서 고치지 않았다. 다른 잔여 테스트 데이터는 삭제하지 않았다. 실패와 집중 통과를 모두 보존했다. 마지막 HTTP 회귀에서 드라이버 검색 환경변수가 없을 때 fixture 초기화 누락도 발견해 테스트가 native PG를 직접 등록하도록 고쳤고 해당 초기 실패도 보존했다.

HTTP MCP 검사는 실PG execute_impl·운영 cache/page helpers와 실제 localhost HTTP 인증/응답을 사용하되 UI transport는 fixture이고, 다른 클라이언트 선택도 테스트 marker로 모사한다. 캐시 단위 검사는 별도로 client/token/session/profile 불일치, LRU 개수·바이트, TTL 경계, 세션·클라이언트 정리, 큰 UTF-8 값을 검사한다. native 앱 GUI와 외부 모델 제공자 E2E, 실제 10분 대기는 하지 않았다. 내장 AI의 기존 명시적 행 공유 토글·20행/100열·128KiB 제한과 Operation 제안 전용 불변식은 유지했고 AI 출력을 실행하는 경로를 추가하지 않았다. Browser WebMCP registry는 기존 count-only 계약으로 남는다.

MySQL true streaming은 채택하지 않았다. QueryResult의 generic Protocol과 별도 read-only operation_connection, 타임존 변환, guarded 취소·정리 경로를 같은 async sink에 연결하려면 별도 리팩터링·검증이 필요하다. 이번에는 capability=false로 두고 기존 MySQL/MariaDB 실DB 계약을 검증했다. 남은 것은 이 확장, Mongo 전역 fixture 격리 문제의 별도 수정, 실제 native 앱·릴리스·제공자 검증이다. 완료 주석이나 mock만으로 실행·성능 완료를 표시하지 않았다.
