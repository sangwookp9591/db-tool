# Tabularis 0.28.0 / AxDB 비교 측정

확정 범위는 기본 big 쿼리 5쌍과 번들 크기다. 유휴 보완은 40분 대기 후 0/6쌍으로 미측정이며 시작·유휴 우열은 판정하지 않는다.

측정일: 2026-10-15 (Asia/Seoul). AxDB 빌드 기준 커밋: `414c8ad4a3a65519670a94bb44d0c338064f92e0`.

## 환경과 범위

- Apple M5, RAM 24 GiB, macOS 27.0.1 (26A434), 같은 로그인 세션, 창 크기 1280×800. 다중 디스플레이 환경이며 전체 시행의 디스플레이 위치/배율 고정은 검증하지 못했다.
- 측정 중 다른 워커가 소스 파일을 변경했지만, 측정한 두 `.app` 실행 파일의 SHA-256은 초기 값과 동일함을 재확인했다. 현재 작업 트리의 기능 변경은 이번 결과에 포함되지 않는다. 재현 시 같은 번들이나 기준 커밋의 별도 체크아웃을 사용한다.
- Tabularis: 제공된 공식 aarch64 0.28.0 `.app`. AxDB: `pnpm --dir ui build` 후 `pnpm dlx @tauri-apps/cli@2 build`로 생성한 release `.app` (DMG도 생성 성공).
- 테스트 PG는 `127.0.0.1:55432/dbtool_test`만 사용한다. 사용자 DB 포트 5432/5439/32802에는 연결하지 않는다.
- Tabularis 설정 경로는 참조 소스 `src-tauri/src/paths.rs`의 `ProjectDirs::from("", "", "tabularis")`에서 확인한 `~/Library/Application Support/tabularis`다. 최초 점검 시 연결/설정 파일은 없었고 업데이트 캐시와 실행 흔적은 있었다. 기존 폴더를 보존하고, GUI에서 만든 테스트 연결 상태와 빈 상태를 분리했다.
- Tabularis 커뮤니티 모달은 `Maybe later`로 닫았다. GUI에서 테스트 URI를 입력해 `compare-pg`를 생성했다. PostgreSQL 플러그인 다운로드 실패 경고가 있었으며, 연결에 성공한 내장 `Deprecated` PostgreSQL 드라이버를 사용했다. 결과는 이 설치 상태에 한정한다.
- AxDB는 기존 e2e 프로필 중 PG 1개만 측정용 디렉터리에 복사했다. 키체인 서비스 `axdb`, 계정 `profile:e2e-pg-0001`의 준비된 테스트 자격 증명을 사용한다. 시작/유휴의 연결 1개 상태는 **저장된 프로필 1개, 열린 세션 없음**이며 두 앱 모두 자동 연결을 사용하지 않는다.

## 방법

코디네이터 보완 지침에 따라 후속 시행은 각 A/B 쌍 직전에 1분 load ≤8을 최대 600초 기다린다. 30초 간격으로 기록하고, 통과와 시간 초과를 구분한다. 결론 표는 통과한 쌍만으로 계산하며 지표별 null을 제외하고 유효 수를 표시한다. 유효 쌍 3개 미만은 표본 부족이다. 초기 게이트 미적용 결과는 별도 참고 표에만 남긴다.

초기 시작/유휴는 빈 상태와 저장 연결 1개 상태 각각 `Tabularis → AxDB`를 5회 반복했다. 보완 계획은 같은 상태별 3쌍이며 별도 파일에 기록한다. 측정 중 빌드는 하지 않는다. 매 시행 직전 `ps`와 `uptime`을 저장한다. 기존 Orca/ChatGPT Node 프로세스는 종료하지 않았으므로 완전히 조용한 머신의 측정은 아니다. 첫 환경 기록의 load average는 14.52/18.79/17.72였다.

`compare_probe.swift`의 창 판정은 기존 `measure_app.swift`와 동일한 CGWindowList 기준(해당 PID, 화면 위 창, 너비와 높이 >200)을 사용한다. 프로브는 컴파일 후 selfcheck(자기 PID의 프로세스 통계, 정규식 탐지, AX 권한)를 통과했다. 시작 시각은 단조 시계의 `Process.run()` 직전이다. 초기 시행은 창과 AX 텍스트를 같은 루프에서 첫 10초 동안 관찰했다. 초기 20회 이후에는 AX 관찰을 별도 스레드로 옮기고 시작 관찰 한도를 30초로 확장했으며, RSS 10초/60초 시점을 따로 유지했다. 앱 창의 AX 트리만 읽으며 OS 메뉴/최근 항목은 수집 대상에서 제외한다. 앱 고유 텍스트는 Tabularis `Connections`, AxDB `CONNECTIONS`의 정확한 일치다. 이는 접근성 텍스트가 나타난 시점의 대용 지표이며 실제 픽셀의 첫 의미 있는 페인트를 직접 측정한 값은 아니다. 재부팅/OS 캐시 비우기를 하지 않아 cold-start 결과로 해석하지 않는다.

RSS 합계에는 공유 페이지가 중복 포함될 수 있으며 JS heap이나 앱이 단독 소유한 RAM과 같은 값으로 해석하지 않는다. 예를 들어 두 프로세스가 같은 공유 라이브러리 페이지를 매핑하면 각 RSS에 포함될 수 있다.

RSS는 실행 약 10초/60초 시점의 앱 PID와 실행 전 목록에 없던 `com.apple.WebKit` PID들의 합이다. 각 PID와 RSS를 원자료에 저장한다. 다른 앱이 동시에 새 WebKit 프로세스를 만들 경우 오귀속 가능성이 있으며, 이 방법은 전용 프로세스 책임 추적보다 약하다. `footprint --noCategories` 출력도 PID 집합마다 보관한다. CPU는 30초와 60초 시점의 같은 집합의 누적 CPU 시간(`ps time`) 차이를 실제 경과 시간으로 나눈 비율이며, 100%는 CPU 코어 1개다. RSS와 번들은 MiB(1024² bytes)로 표기하며 footprint는 OS 출력의 반올림된 MB를 그대로 표시한다.

원래 명세에는 `SELECT * FROM e2e.big`(원본 250,000행/2컬럼)과 `SELECT g, md5(g::text), now() FROM generate_series(1,100000) g`가 있었다. 이번 정식 쿼리 측정은 기본 big 조건(Tabularis 500행, AxDB 1,000행)만 수행했다. 생성 쿼리와 동일 100,000행 조건은 범위 조정으로 미측정이다. 전체 25만 행을 렌더링한 결과가 아니다.

준비 점검 후 Tabularis는 새 빈 콘솔에 AX set-value를 적용하고, AxDB는 편집기 좌표 클릭 → 전체 선택 → type-text를 사용한다. AxDB의 AX set-value는 편집기에서 기존 SQL로 복원되거나 다른 필드로 적용되는 문제가 있어 사용하지 않는다. SQL이 정확히 일치하고 이전 첫 행 값이 없는지 확인한 뒤에만 계측한다. 창 생성 후 명시적으로 `open -a`로 앱을 활성화한다. 쿼리 실행은 두 앱 모두 편집기에서 `Cmd+Return`을 보내고 외부 AX 폴링으로 결과 값과 행 수 텍스트를 관찰한다. 표시되는 결과 수는 실제로 가져온 행 수다. Tabularis는 현재 페이지의 retrieved rows, AxDB는 현재 보관된 loaded/result rows를 관찰하며, 전체 데이터의 별도 COUNT 시간은 포함하지 않는다. 앱 내부 쿼리 시간과 외부 시간을 섞지 않는다.

## 게이트 통과 쿼리 결과: 기본 `e2e.big`

유효 A/B 5쌍, 총 10개 시행이며 모두 게이트 통과와 첫 행/결과 수 감지가 확인됐다. Tabularis는 **500행**, AxDB는 **1,000행**을 가져오는 기본값이다. 표는 중앙값 (최소~최대)이며 차이는 반올림 전 중앙값으로 계산한 AxDB − Tabularis다.

| 항목 | Tabularis | AxDB | 차이 |
|---|---:|---:|---:|
| 첫 행 AX 관찰 (ms) | 221 (175~388) | 163 (128~238) | -58 |
| 결과 수 AX 관찰 (ms) | 222 (175~389) | 163 (129~239) | -58 |
| 결과 표시 후 RSS (MiB) | 411.9 (374.2~517.5) | 202.2 (200.7~233.5) | -209.6 |
| 결과 표시 후 footprint 요약 (OS 표시 MB, 반올림) | 428 (385~432) | 187 (174~188) | -241 |
| 스크롤 끝 행 검증 | 0/5, 시간 미확정 | 0/5, 시간 미확정 | 비교 불가 |

첫 행과 결과 수가 같은 AX 스캔에서 나타나면 둘 사이의 정밀한 시간차는 구분할 수 없다. AX 트리 크기와 순회 비용도 관찰 지연에 포함된다. 기본 행 수가 달라 이 결과를 동일 처리량의 대량 결과 성능으로 일반화할 수 없다.

| 조건 | 계획 | 정식 측정 | 상태 |
|---|---:|---:|---|

측정 앱이 종료된 게이트 대기 중에도 높은 부하와 cargo/rustc가 관측됐다. 코디네이터는 동시 워커 빌드에 따른 외부 부하임을 전달했다. 해당 부하를 측정 앱의 문제로 해석하지 않는다. 유휴 보완 게이트는 load ≤8과 빌드 프로세스 부재를 함께 확인하고, 단계 누적 대기 상한은 40분이다. 상한 뒤 남은 쌍은 미측정(부하)으로 기록한다.

`compare_idle.py`는 각 Tabularis 시행 중에만 기존 폴더를 `tabularis-preserved`에 옮긴 뒤 `finally`에서 복구한다. 강제 중단했다면 보존 폴더 존재 여부를 먼저 확인한다. 프로브를 다시 컴파일할 때는 측정이 진행 중이면 안 된다.

## 부하 게이트 적용 전의 참고 결과

아래는 처음 실행한 각 5회씩, 총 20개 유휴 시행이다. 시행 직전 부하는 7.12~110.13이었으며 부하 게이트는 적용하지 않았다. 따라서 **성능 우열의 결론 표에 사용하지 않는다**. null은 각 지표 집계에서 제외하며 유효 수/전체 수를 표시한다. 초기 프로브는 창과 AX를 첫 10초까지만 관찰했다. 이후 프로브를 30초, 별도 AX 관찰 스레드로 보완했다. 초기 데이터는 덮어쓰지 않았다.

## 준비 점검과 제외 기준

[준비 점검 원자료](results-compare-preflight.json)는 두 앱의 기본 결과와 AxDB 100,000행 표시를 실제로 확인한 기록이다. 이 단계의 시간은 부하 게이트가 없고 추가 관찰이 개입했으므로 성능 집계에서 제외한다. [잘못된 SQL 입력 시행](results-compare-query-failures.json)은 이전 콘솔 복원과 입력 선택 문제로 SQL이 중복된 경우이며, 성능 결과로 사용하지 않는다. 앱 등록/창 생성 전 조회 실패, 포커스 상실, 포커스 설명 행을 편집기로 중복 선택한 검증기 오류도 계측 전 준비 실패로 기록했다.

초기 AX 미감지에는 높은 부하뿐 아니라 배경 앱의 활성화/occlusion 영향이 있을 수 있다. 배경 상태에서 창 5개 AX 노드만 노출하던 AxDB가 `open -a` 직후 전체 UI를 노출하는 것을 관찰했다. 이후 시작 프로브는 첫 창을 감지하면 두 앱 모두 명시적으로 활성화한다. 초기와 보완 시행을 합쳐 하나의 시작 중앙값을 만들지 않는다.

스크롤 도구의 성공 응답은 끝 도달의 증거가 아니다. 마지막 행의 MD5 값이 AX 트리에 보인 경우만 끝 도달과 시간을 기록하고, 보이지 않으면 시간은 null로 둔다. 스크롤/드래그와 대상 PID 직접 이벤트도 준비 점검에서 시도했으나 끝 행 미확인을 성공으로 보고하지 않았다. 정밀 FPS는 측정하지 않는다.

준비 점검에서 별도로 수행한 Swift 프로브 8개도 [준비 점검 원자료](results-compare-preflight.json)에 보존했다. 이 중 첫 행 미감지는 1개, 결과 수 미감지는 4개이며 전부 결론 집계에서 제외한다. 이전 결과가 남았거나 입력 경로가 검증되지 않은 준비 점검의 숫자를 정상 성능 표본으로 사용하지 않는다.

## 해석과 남은 한계

확정된 기본 big 조건에서는 AxDB의 첫 행 AX 관찰과 결과 표시 후 RSS 중앙값이 낮았다. 기본 행 수가 500/1,000으로 다르고 AX 순회 비용도 포함되므로, 같은 행 수에서의 처리 성능이나 실제 첫 픽셀의 차이로 일반화하지 않는다.

두 앱 모두 Tauri/WebKit을 사용한다. 참조 소스에서 Tabularis 0.28.0은 React·Monaco와 TanStack 기반 DataGrid, AxDB는 Preact·CodeMirror와 VirtualTable을 사용하며 두 결과 표 모두 행 가상화를 구현한다. 기능 범위와 라이브러리 구성이 번들 크기 및 런타임 메모리에 기여했을 가능성은 **추정**이다. 각 요소의 기여분을 분리하는 실험은 수행하지 않았다.

공유 머신의 동시 워커 빌드와 부하 변동, 앱 활성화 및 AX 관찰 비용, 고정하지 못한 디스플레이 배율, OS/DB/WebKit 캐시의 영향을 완전히 통제하지 못했다. 결과는 이 머신·설치 상태·기본 big 조건의 관측값이다. 동일 100k와 생성 쿼리는 미측정이며, 스크롤 끝 도달과 정밀 FPS는 미검증이다.

검증은 실제 release 앱의 쿼리 관찰 10개와 [프로브/입력·게이트/원자료 검증 기록](results-compare-validation.txt)을 근거로 한다. 금지 포트 검사는 임시 JSON 입력으로 거부 경로를 확인했으며 해당 DB에는 접속하지 않았다. 애플리케이션 소스는 이 워커가 수정하지 않았고 전체 앱 테스트 스위트는 실행하지 않았다.

측정/준비 과정에서 띄운 release 앱과 PostgreSQL 플러그인 잔류 프로세스가 없음을 최종 `ps`로 확인했고, Tabularis 보존 폴더가 남아 있지 않아 설정 복구 상태를 확인했다. 이 워커는 커밋하지 않았다. 다른 워커의 소스·벤치 파일 변경은 보존했다.

## P1 이후: 최종 기능 기준 유휴 재비교

최종 기능 커밋 `85231f2` release를 대상으로 `compare_idle.py --p1-after`로 재측정했다. 최적화 후보는 모두 채택하지 않았으므로 AxDB 전/후의 실행 파일 SHA-256은 같다. 따라서 아래 전/후 차이를 최적화 효과로 해석하지 않는다. Tabularis는 동일한 공식 0.28.0 바이너리다.

빈 설정/저장 PG 프로필 1개 상태별로 세 앱을 3회 교대하고 짝수 시행은 순서를 뒤집었다. 열린 DB 세션은 없었다. 게이트는 1분 load ≤8 + 빌드 없음이며 누적 대기는 0.54초로 40분 상한 이내였다. 18/18이 부하·빌드·창/AX 준비 검사를 통과했고 프로세스는 앱 1 + WebKit 3개였다. 값은 중앙값(최소–최대)이며 n=3이다.

이 조건에서 최신 AxDB의 유휴 RSS는 Tabularis보다 낮게 관측됐다. CPU는 작은 값이며 30초 구간의 약 0.033%p 해상도 근처이므로 저장 프로필 상태의 차이를 우열로 해석하지 않는다. 이 비교는 기능 범위·플러그인 구성·캐시 상태가 다른 두 설치에 한정하며 보편적인 우열이나 cold-start 결과로 확대하지 않는다. 특히 P1 계측 모드의 50초 CPU 구간과 이번 일반 앱의 30초 구간은 직접 같은 표본으로 합치지 않는다.

모든 실행한 앱 PID가 종료됐고 Tabularis 원본 설정 폴더가 복원됐으며 보존용 임시 백업은 남지 않았다. 유휴 측정 후에만 Rust 테스트/빌드를 시작했다.
